# LM-3: SRE-платформы — варианты интеграций и целевая функциональность

## 1. Контекст задачи

Агент документирования инцидентов (llmortem) предполагает интеграции с распространёнными SRE/DevOps-платформами. Цель интеграций — автоматизировать сбор фактов об инциденте (сигналы, изменения, коммуникации), восстановить временную линию событий и использовать накопленный контекст для генерации постмортемов и подсказок дежурным.

Под «SRE-платформами» в рамках данной задачи понимаются несколько классов систем:
- observability/monitoring/alerting (метрики, логи, трассировки, алерты);
- incident management / on-call / IRM (объявление инцидента, роли, эскалации, артефакты, PIR);
- SCM/CI/CD (коммиты, релизы, деплой, pipeline, изменения конфигураций);
- knowledge base / docs / runbooks (ранбуки, инструкции, архитектурные описания);
- ChatOps/мессенджеры (фактология из обсуждений и действий в инцидентных каналах).

В описании задачи приведены примеры (Grafana, “Sage”, Docusaurus, GitLab). По факту целесообразно проектировать интеграционный слой так, чтобы поддерживать несколько популярных представителей каждого класса.

## 2. Принципы интеграции: что агент должен уметь получать и что должен уметь делать

Интеграции целесообразно оценивать по двум осям:

### 2.1. Какие данные извлекать (Read-поток)
1) **Сигналы обнаружения**: алерты, связанные метрики/логи/трейсы, severity, затронутые сервисы.
2) **Временная линия**: события и действия (создание инцидента, обновления статуса, сообщения, изменения, запуск процедур).
3) **Контекст изменений**: релизы, деплои, конфиг-диффы, feature flags, миграции, изменения инфраструктуры.
4) **Контекст знаний**: релевантные ранбуки, документация, прошлые постмортемы, паттерны.
5) **Результаты анализа**: гипотезы причины, подтверждения/опровержения, принятые решения.

### 2.2. Какие действия выполнять (Write/Action-поток)
1) Создавать/обновлять артефакты: постмортем, PIR, задачи (action items), ссылки на доказательства.
2) Обогащать инцидентную карточку: добавить таймлайн-ивенты, связать алерты/тикеты/PR.
3) Предлагать и выполнять безопасные автоматизации (без “самовольных” изменений продакшена): сформировать MR/PR с фиксами, открыть issue, сформировать план, сгенерировать шаблон сообщения.

## 3. Анализ интеграций по платформам и классам

Ниже приведены наиболее “прикладные” точки интеграции — то, что даст максимальную пользу именно для автоматического документирования инцидента.

### 3.1 Observability / Alerting / On-call: Grafana (OnCall / IRM / Alerting)

**Потенциальные данные (Read):**
- входящие алерты как первичный сигнал (включая labels/annotations и метаданные маршрутизации);
- контекст интеграции: откуда пришёл алерт, группировка и связка алертов в инцидент;
- события эскалации и оповещения.

Grafana OnCall поддерживает интеграции как точку входа алертов через API URL и отдельный HTTP API для управления интеграциями/алертами. :contentReference[oaicite:0]{index=0}  
В Grafana Alerting активно используются labels/annotations как структурированная часть сигнала (удобно для последующего извлечения сущностей: сервис, команда, среда, регион). :contentReference[oaicite:1]{index=1}  
Grafana IRM позиционируется как набор инструментов для координации реагирования и документирования инцидентов. :contentReference[oaicite:2]{index=2}

**Потенциальные действия (Write/Action):**
- привязка алертов к “инцидентной сущности” llmortem (через ID/ссылки);
- автоматическое сохранение важной фактологии в таймлайн (например, “alert fired”, “escalation”, “ack”);
- генерация черновика постмортема с ссылками на соответствующие алерты и панели.

**Практическая ценность для llmortem:**
- Grafana-поток обеспечивает объективную “точку старта” таймлайна;
- labels/annotations уменьшают ручной труд по структурированию инцидента;
- IRM/OnCall-данные позволяют отличать “шум” от событий, реально влияющих на управление инцидентом.

---

### 3.2 SCM/CI/CD и изменения: GitLab

**Потенциальные данные (Read):**
- коммиты, merge request’ы, диффы, обсуждения и решения ревью;
- issues/тикеты, связанные релизные заметки;
- статус и результат CI/CD pipelines.

GitLab предоставляет REST API для основных сущностей разработки, включая merge requests и issues. :contentReference[oaicite:3]{index=3}

**Потенциальные действия (Write/Action):**
- создание issue на action items и связывание с инцидентом;
- формирование MR-шаблона с предполагаемым фикс-подходом (как “предложение”, не как автодеплой);
- комментарии в MR/issue с извлечённой фактологией и ссылками (например, на алерты/логи).

**Практическая ценность для llmortem:**
- GitLab-данные позволяют строить причинно-следственные гипотезы через “changes correlation” (что изменилось незадолго до инцидента);
- формирование action items и контроль их выполнения естественно ложится на issue/MR flow;
- наличие security-разделов (уязвимости/отчёты) также может быть релевантно в отдельных инцидентах. :contentReference[oaicite:4]{index=4}

---

### 3.3 Knowledge base / Runbooks: Docusaurus

**Потенциальные данные (Read):**
- контент ранбуков, архитектурных заметок и инструкций (Markdown/MDX);
- структура документации (разделы, навигация, теги/категории, ссылки).

Docusaurus использует Markdown как основной формат и поддерживает MDX (Markdown + JSX). :contentReference[oaicite:5]{index=5}  
Для интеграции с LLM полезны механизмы, обеспечивающие доступ к исходникам документов в “сыром” виде (например, через плагины, публикующие markdown-источники). :contentReference[oaicite:6]{index=6}

**Потенциальные действия (Write/Action):**
- генерация/обновление черновика постмортема как Markdown/MDX-документа в репозитории документации;
- автоматическое формирование секции “Runbook used / References” с точными ссылками на страницы;
- предложение правок в ранбуки по итогам инцидента (как отдельные изменения, проходящие review).

**Практическая ценность для llmortem:**
- ранбуки — основной “бизнес-контекст” SRE-процесса: что считать инцидентом, какие сервисы критичны, какие действия допустимы;
- интеграция позволяет превратить постмортем в стандартный документ внутри текущей экосистемы документации.

---

### 3.4 Incident management / PIR: альтернативный «пласт» (на примере :contentReference[oaicite:7]{index=7})

Даже если в целевой организации выбран другой IRM-инструмент, класс “incident management + post-incident review” важен как точка интеграции: именно там живут статусы инцидента, роли, PIR и action items.

В экосистеме JSM существует отдельный REST API для инцидентов, включая сущности вроде post-incident review. :contentReference[oaicite:8]{index=8}

**Практическая ценность для llmortem:**
- “официальная карточка инцидента” часто хранится вне observability и кода;
- PIR/постмортем как формальная сущность упрощает согласование и аудит.

---

### 3.5 Error tracking / product incidents: :contentReference[oaicite:9]{index=9}

**Потенциальные данные (Read):**
- ошибки и “issues” (группы событий), частотность, теги, релизы, затронутые окружения;
- события по конкретной ошибке/инциденту.

Sentry предоставляет API для событий/ошибок (issues/events), что позволяет использовать эти данные как источники фактов для инцидентного таймлайна и анализа. :contentReference[oaicite:10]{index=10}

**Потенциальные действия (Write/Action):**
- прикрепление ссылок на конкретные issues и релизные маркеры к постмортему;
- сохранение “корневых” ошибок как доказательной базы.

**Практическая ценность для llmortem:**
- ошибки приложения часто являются первичным симптомом пользовательского impact;
- данные из error tracking позволяют связать инцидент с конкретным типом отказа и релизом.

---

### 3.6 Incident management (SaaS пример): :contentReference[oaicite:11]{index=11}

Datadog имеет отдельный модуль incident management и поддерживает API для инцидентов. :contentReference[oaicite:12]{index=12}  
Также описывается использование инцидентного timeline как первичного источника информации о ходе реагирования. :contentReference[oaicite:13]{index=13}

**Практическая ценность для llmortem:**
- схожие сущности (incident, timeline, postmortem) подтверждают, что “инцидентная сущность + таймлайн” является индустриальным стандартом;
- интеграция позволяет переносить идеи llmortem на разные экосистемы.

---

### 3.7 ChatOps / коммуникации: :contentReference[oaicite:14]{index=14} (как пример)

Мессенджеры являются важнейшим источником фактологии: кто что сделал, какие гипотезы обсуждали, какие решения приняли. В Slack доступна выгрузка истории сообщений через API методов вроде `conversations.history`. :contentReference[oaicite:15]{index=15}  
При этом экспорт/доступ к истории может зависеть от плана и административных настроек, что является организационным ограничением интеграции. :contentReference[oaicite:16]{index=16}

**Практическая ценность для llmortem:**
- чат — ключ к восстановлению таймлайна “человеческих” действий и решений;
- ограничения экспорта подчёркивают важность абстракции интеграции (разные мессенджеры — разные условия доступа).

## 4. Отдельный комментарий про “Sage” из постановки задачи

Термин “Sage” в индустрии не является однозначным названием конкретной SRE-платформы: под него могут подпадать внутренние решения компаний или разные продукты/бренды. В отсутствие уточнения целесообразно трактовать “Sage” как:
- либо внутреннюю платформу наблюдаемости/инцидентов конкретной организации,
- либо абстрактную “ещё одну SRE-платформу”, поддержку которой можно обеспечить через общий механизм коннекторов.

Отсюда следует практическое требование: интеграционный слой llmortem должен быть модульным и расширяемым (коннекторы/адаптеры), чтобы подключение новой “Sage-like” системы не требовало изменения ядра агента.

## 6. Выводы

1) Интеграции с SRE-платформами целесообразно рассматривать как комбинацию источников фактологии: observability (сигналы), SCM/CI (изменения), docs/runbooks (контекст), incident management (формальные сущности), ChatOps (действия и решения).  
2) Наиболее “несущий” для автоматизации документирования компонент — единая временная линия, формируемая из событий разных систем (алерты, изменения, сообщения, статусы).  
3) Архитектурно требуется модульный интеграционный слой, позволяющий добавлять новые платформы и внутренние системы (“Sage-like”) без модификации ядра агента.
